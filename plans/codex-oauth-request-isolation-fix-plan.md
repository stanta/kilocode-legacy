# План исправления OAuth и жизненного цикла запросов Codex

Дата: 2026-11-13. Статус: проект для согласования; исправления поведения ещё не реализованы.

## 1. Цель, доказательства и границы

Обеспечить независимое выполнение задач в разных локальных окнах VS Code при использовании одной подписки ChatGPT: согласованное обновление OAuth, реальная отмена сети, ограниченное ожидание и отсутствие склейки ответов разных попыток.

Подтверждено исследованием:

- OAuth-кэш и объединение refresh существуют только в одном экземпляре менеджера; другой экземпляр может обновить старый токен и удалить более новые общие credentials: [OAuth-менеджер](../src/integrations/openai-codex/oauth.ts:343).
- Любая ошибка SDK переводит выполнение на новый SSE-запрос, включая ошибку после частичного ответа: [транспорт провайдера](../src/api/providers/openai-codex.ts:381).
- Отмена задачи прерывает ожидание, но её сигнал не передаётся провайдеру: [создание запроса](../src/core/task/Task.ts:5206).
- Резервный транспорт не имеет собственного явно заданного дедлайна: [SSE-запрос](../src/api/providers/openai-codex.ts:620).
- Повторы есть также в [цикле задачи](../src/core/task/Task.ts:4020), [первом фрагменте](../src/core/task/Task.ts:5388) и [обёртке переключения провайдеров](../src/api/providers/virtual-quota-fallback.ts:75).
- В реальных журналах двух окон найдены HTTP 403 при refresh и сетевой сбой. Причина конкретного 403 не установлена; тестовая гонка refresh не доказывает происхождение этих отказов.
- Предыдущая проверка: 44 целевых теста Codex прошли, включая диагностические воспроизведения существующих дефектов. Это не свидетельство исправности изоляции.

Основная область: локальные окна одного пользовательского окружения VS Code, имеющие общее хранилище секретов. До реализации проверить, совпадают ли границы этого хранилища и выбранного каталога блокировки, в том числе для профилей VS Code.

Не включать автоматически:

- переделку всех провайдеров и общий планировщик запросов аккаунта;
- исправление статического парсера native tools — отдельная подтверждённая проблема задач одного процесса;
- миграцию или ручное исправление сохранённых диалогов;
- обход HTTP 403, региональных/сетевых ограничений или квот;
- гарантию координации разных компьютеров, Remote SSH, контейнеров и независимых установок, не имеющих общего lock-домена.

Agent Manager требует отдельной интеграции: дочерний процесс использует [копию секретов в памяти](../packages/agent-runtime/src/host/VSCode.ts:953). Файловая блокировка сама по себе не обновляет эту копию. Дополнительный этап описан ниже; нельзя объявлять его покрытым исправлением обычных окон.

## 2. Обязательные инварианты

1. В одном домене credentials выполняется не более одного refresh одновременно; блокировка удерживается до завершения сохранения.
2. После получения блокировки credentials перечитываются из источника истины, а не берутся из старого кэша.
3. Старый запрос не удаляет и не перезаписывает credentials, изменённые входом, выходом или другим окном.
4. Отмена одного ожидающего OAuth-клиента не отменяет общий refresh, нужный другому клиенту.
5. Отмена задачи достигает её сетевого запроса и не затрагивает соседнюю задачу.
6. Один выходной поток модели принадлежит одной принятой попытке ответа. После частичного ответа автоматического replay нет ни в провайдере, ни выше.
7. У запроса есть конечный бюджет ожидания, покрывающий авторизацию, открытие соединения и чтение тела.
8. Все слушатели, таймеры, reader и блокировки освобождаются при успехе, ошибке и отмене.
9. Токены остаются в SecretStorage; lock-файлы, обычные логи и тестовые артефакты не содержат production-секретов.

## 3. Архитектурное решение

### OAuth: локальный single-flight + межпроцессный lock + перечитывание

Переиспользовать установленную Proper Lockfile; пример использования уже есть в [safeWriteJson](../src/utils/safeWriteJson.ts:40). Не использовать сам JSON-writer для хранения токенов и не создавать собственную библиотеку блокировок.

Добавить узкий OAuth-specific helper для блокировки, без универсального coordinator-framework. Новый планируемый файл: [oauth-refresh-lock.ts](../src/integrations/openai-codex/oauth-refresh-lock.ts).

Lock-домен определяется общим доменом хранилища credentials. Не использовать workspace, ID задачи, модель, текущее значение токена или временный каталог агента как ключ блокировки. Исходный кандидат — общий каталог расширения, но его соответствие SecretStorage между профилями должно быть проверено до фиксации решения.

Все штатные операции записи и удаления credentials используют один lock. Внутри lock вызываются внутренние операции хранения без повторного захвата, чтобы исключить deadlock.

Событие изменения секрета инвалидирует кэш, но не заменяет блокировку и не даёт атомарного compare-and-swap. Проверка версии и запись безопасны только при участии всех писателей в одном протоколе.

### Запросы: локальный контекст выполнения и один владелец повторов

Сигнал отмены передавать отдельным необязательным четвёртым аргументом локальных options в [контракте API](../src/api/index.ts:146), а не включать в metadata, тело запроса, IPC-конфигурацию или историю. Существующие три аргумента остаются совместимыми. Обёртки, делегирующие вызов, обязаны передать options дальше.

Провайдер Codex владеет конкретным транспортом и его освобождением. Цикл задачи владеет ограниченным повтором до начала ответа. Обновление авторизации после явного HTTP 401 допускается отдельно, однократно и до принятия ответа. SDK-ретраи отключаются для Codex, чтобы бюджеты не перемножались.

3. Подготовить синтетическое secret-хранилище с событиями, задерживаемой записью и двумя менеджерами; управляемый поток SDK/SSE; виртуальные часы.
4. Отдельно подготовить тест двух дочерних процессов с общим lock-каталогом и искусственным источником credentials. Два объекта в одном процессе не доказывают работу межпроцессной блокировки.

### Этап 1. Согласовать OAuth-кэш и локальный refresh

Файлы: [oauth.ts](../src/integrations/openai-codex/oauth.ts), [инициализация расширения](../src/extension.ts:181). Новый тестовый файл: [oauth.spec.ts](../src/integrations/openai-codex/__tests__/oauth.spec.ts).

1. Подписаться на изменение нужного секрета; повторная инициализация снимает старую подписку. Добавить корректное освобождение при остановке расширения.
2. Отсутствие или невалидность сохранённого секрета сбрасывает старый кэш. Не возвращать прежний access token после внешнего выхода из аккаунта.
3. Защитить кэш от завершения более старого асинхронного чтения после нового события: локальный счётчик версии/invalidation и повторное чтение при необходимости.
4. Объединить обычный и принудительный refresh в одну внутреннюю операцию. Single-flight охватывает чтение, refresh и сохранение, а не только HTTP.
5. Сбрасывать ссылку на выполняющуюся операцию только её владельцу и только после её завершения; старое завершение не должно стереть ссылку на новую операцию.
6. Предоставлять провайдеру согласованный снимок access token + account ID из одной версии credentials; исключить раздельное чтение разных аккаунтов в одном запросе.
7. Проверки UI-статуса не должны сами запускать сетевой refresh при каждом обновлении состояния: [текущий потребитель](../src/core/webview/ClineProvider.ts:3013). Отделить «сохранён вход» от получения действующего токена для запроса.

Тесты: внешний login/logout; пропущенное событие с перечитыванием перед refresh; два локальных потребителя; задержанная запись; устаревшее чтение; повторная инициализация; UI не обращается к token endpoint.

### Этап 2. Сериализовать refresh между окнами

Файлы: [oauth.ts](../src/integrations/openai-codex/oauth.ts), новый [oauth-refresh-lock.ts](../src/integrations/openai-codex/oauth-refresh-lock.ts).

Порядок операции:

1. Зафиксировать версию credentials, с которой был получен отказ, если refresh принудительный.
2. Получить lock с ограниченным ожиданием. Отмена ожидания одного запроса не отменяет уже начатый общий refresh.
3. После захвата заново прочитать SecretStorage. При отсутствии credentials завершиться без сетевого refresh.
4. Если другое окно уже обновило токен и он действителен, использовать его. При принудительном refresh сравнивать именно версию отклонённого токена, а не только срок действия.
5. Обновить токен под блокировкой с конечным сетевым таймаутом. Полученный ответ валидировать.
6. Проверить, что операция всё ещё владеет lock, credentials не сменились и не был выполнен logout; сохранить новую версию.
7. Освободить lock в гарантированной очистке, не маскируя исходную ошибку ошибкой освобождения.

Практические ограничения:

- Lock-содержимое не включает токены, email, account ID или prompt.
- Одинаковые настройки свежести и heartbeat у всех писателей. Не копировать короткий retry-бюджет JSON-writer: он не рассчитан на сетевой refresh.
- Ожидание lock и refresh ограничены явно; при таймауте нельзя продолжать refresh без lock.
- При утрате lock отменить сетевую операцию, запретить сохранение и сообщить управляемую ошибку. Не бросать необработанное исключение из callback компрометации.
- Stale-lock recovery не даёт распределённой exactly-once гарантии: падение после серверной ротации, но до сохранения может потребовать повторного входа. Не обещать автоматического восстановления неизвестного нового токена.
- Пропущенное событие SecretStorage не должно ломать корректность. Проверить свежесть чтения между процессами под lock; если платформа возвращает старое значение, файлового lock недостаточно — остановить выпуск этого решения и выбрать единственного владельца credentials.

Тесты: два процесса → один refresh; второй читает новое значение; принудительные 401 на одной версии → один refresh; занятой/устаревший lock; отказ записи; потеря lock; отсутствие секретов в файловой системе.

### Этап 3. Безопасные ошибки OAuth, login и logout

Файлы: [oauth.ts](../src/integrations/openai-codex/oauth.ts:117), [потребитель авторизации Codex](../src/api/providers/openai-codex.ts:195).

1. Сохранить тип ошибки, HTTP-статус и нормализованную категорию. Не превращать любой отказ refresh в общее «не авторизован».
2. Отсутствие credentials — отдельный результат; сетевой сбой, таймаут, 403, 429 и серверные ошибки — типизированные отказы без удаления секрета.
3. Для явного invalid grant перечитать текущую версию под lock. Более новые credentials не удалять. Консервативный вариант: сообщить о необходимости повторного входа, оставив секрет до явного logout/замены; не выполнять слепое глобальное удаление.
4. Login, logout и сохранение refresh согласовать одним lock-протоколом. Не удерживать lock во время ожидания браузерного входа; захватывать на commit. Состояние устаревшей операции входа после logout не должно воскресить сессию.
5. Во время смены аккаунта текущий запрос не переходит незаметно на другой аккаунт; следующий запрос получает новый согласованный снимок.
6. Журналы — по белому списку полей. Не выводить сырые тела ошибок token endpoint.

Тесты: новый login во время refresh; logout во время refresh; stale failure после успешного обновления другим окном; 403 и timeout не удаляют секрет; access token и account ID принадлежат одной версии.

### Этап 4. Провести реальную отмену от задачи до транспорта

Файлы: [контракт API](../src/api/index.ts:146), [Task](../src/core/task/Task.ts:5206), [Codex](../src/api/providers/openai-codex.ts), [обёртка fallback](../src/api/providers/virtual-quota-fallback.ts:75), [сжатие контекста](../src/core/condense/index.ts:347).

1. Добавить локальные request options с необязательным сигналом; перечислить все делегирующие обёртки и провести options сквозь них.
2. Создавать контроллер до запуска авторизации/запроса и передавать его провайдеру. Для ручного сжатия контекста передать сигнал его операции, не создавать неконтролируемый запрос.
3. В Codex объединить сигнал пользователя с локальным контроллером дедлайна; предварительно отменённый сигнал не должен приводить к отправке HTTP.
4. Отмена ожидания общего OAuth-refresh прекращает ожидание только этого потребителя. Общая операция продолжает работу для других потребителей и сохраняет результат.
5. При остановке сначала отменить transport, затем закрыть iterator/reader. Не ждать закрытия генератора, зависшего на сетевом чтении, до отправки abort.
6. Обрабатывать отмену до веток auto-retry и provider fallback; не показывать её как сбой модели.
7. При очистке Task сбрасывать контроллер только если он всё ещё принадлежит завершающемуся запросу. Старый finally не трогает контроллер нового запроса.
8. Контрольный тест на реальном локальном HTTP-сервере подтверждает закрытие соединения, а не только вызов метода abort.

Тесты: отмена до токена, в ожидании lock, до заголовков, во время чтения, во время retry delay; задача A отменена, B продолжает; после отмены нет нового HTTP-запроса и нет записи поздних фрагментов в историю.

### Этап 5. Изолировать состояние запроса и владение handler

Файлы: [Codex handler](../src/api/providers/openai-codex.ts:53), [Task](../src/core/task/Task.ts), [condense](../src/core/condense/index.ts:326).

1. Перенести контроллер, текущую идентичность инструмента, счётчики ответа, terminal-state и результаты parsing в контекст конкретного вызова, передаваемый процессору событий.
2. Сохранить существующие getters метаданных для совместимости, но публиковать метаданные только завершившейся допустимой операции, не из позднего потока отменённого запроса.
3. Минимальный контракт: один активный запрос на экземпляр Codex handler. Повторный конкурентный вызов явно отклоняется до сброса состояния; не ставить скрыто в бесконечную очередь.
4. Найти потребителей, которым нужна конкуренция, и дать отдельный handler, прежде всего сжатию контекста. Разные задачи и окна продолжают работать параллельно.
5. Не использовать один изменяемый current-controller для нескольких сетевых попыток; завершение старой попытки не освобождает ресурсы новой.

Тесты: два handler независимы; перекрывающийся вызов одного handler не портит первый; старое завершение не меняет response metadata нового запроса; сжатие не смешивается с основным потоком.

### Этап 6. Ввести единый дедлайн для SDK и SSE

Файлы: [timeout-config](../src/api/providers/utils/timeout-config.ts:10), [Codex](../src/api/providers/openai-codex.ts).

1. Переиспользовать существующую настройку API timeout, не вводить новую панель настроек.
2. Явно закрепить семантику Codex: положительное конечное значение задаёт бюджет; отсутствие, невалидное/бесконечное значение и режим «SDK default» дают стандартные 600 секунд. Не превращать отсутствие явного значения в бесконечный fetch.
3. Бюджет начинается при запуске логического запроса, охватывает OAuth-ожидание, открытие и чтение тела. Однократный auth-retry использует остаток, а не новый полный бюджет.
4. У refresh сохранить отдельный максимум 30 секунд на token endpoint; у совместного refresh собственный бюджет, отмена одного потребителя его не обрывает.
5. Таймер abort действует после получения заголовков и во время чтения SSE. Настройки SDK дополнительно согласованы с остатком времени; не полагаться только на SDK timeout.
6. Таймаут и отмена пользователем — разные причины; классификация сохраняется при прохождении вверх.
7. Очистить таймеры и слушатели на всех выходах, включая раннее завершение потребителем.

Тесты виртуального времени: зависание авторизации, SDK-open, fetch-open, чтения после HTTP 200; остаток бюджета при auth-retry; нулевое/невалидное значение настройки; отсутствие таймеров после завершения.

### Этап 7. Сделать повторы ограниченными и безопасными

Файлы: [Codex transport](../src/api/providers/openai-codex.ts:381), [Task first-chunk retry](../src/core/task/Task.ts:5388), [Task mid-stream retry](../src/core/task/Task.ts:4020), [virtual-quota-fallback](../src/api/providers/virtual-quota-fallback.ts:101).

1. Удалить catch-all переход SDK → SSE. Обычный сетевой/API/stream-сбой не означает несовместимость SDK.
2. Выбирать транспорт до dispatch. SDK остаётся основным; SSE допустим только при заранее установленной недоступности SDK-пути. Не считать отсутствие iterable после уже отправленного запроса доказательством, что сервер ничего не начал.
3. Если fallback действительно необходим в будущем после dispatch — отдельное решение с доказательством безопасности/возобновления; не включать его в эту починку.
4. Отключить автоматические SDK retries для Codex. Единственный общий бюджет безопасных повторов принадлежит Task; стартовое правило — не более двух автоматических повторов до ответа, каждый после подтверждённого закрытия предыдущего запроса.
5. Различать HTTP-отказ до начала ответа и неопределённый исход сетевого запроса. Ошибка без полученных фрагментов сама по себе не доказывает, что сервер не начал генерацию.
6. При получении ответа/фрагментов, вызова инструмента либо неопределённом исходе после принятия запроса устанавливать запрет автоматического replay. Не ждать первого показанного текста: reasoning/tool-delta также считаются частичным ответом.
7. Сохранить машинно-читаемую классификацию ошибки при прохождении через Task и обёртки. Текстовый regex по «401» не должен управлять refresh.

| Ситуация                                              | Действие                                                                  |
| ----------------------------------------------------- | ------------------------------------------------------------------------- |
| Отмена пользователем                                  | Закрыть сеть и закончить; без повторов                                    |
| Явный HTTP 401 до начала ответа                       | Один согласованный refresh и повтор с новым токеном в остатке бюджета     |
| Повторный 401, отсутствие credentials, invalid grant  | Остановить, запросить повторный вход                                      |
| HTTP 400/403                                          | Остановить; не менять транспорт, не запускать общий auto-retry            |
| HTTP 429 или явный 5xx до ответа                      | Ограниченный retry по политике Task и Retry-After; без transport fallback |
| Ошибка сети с неизвестным исходом, EOF без завершения | Остановить текущую попытку, дать явное продолжение пользователю           |
| Любая ошибка после начала ответа                      | Не переигрывать историю автоматически; сохранить статус прерывания        |
| Таймаут                                               | Закрыть сеть; автоматический повтор не продлевает бюджет бесконечно       |

Тесты должны проходить через верхний цикл задачи и обёртку, а не только через handler. Проверить отсутствие повторного исполнения инструмента после обрыва и отсутствие смены провайдера после частичного ответа.

### Этап 8. Завершение потока и целостность истории

Файлы: [процессор Codex](../src/api/providers/openai-codex.ts), [сохранение Task](../src/core/task/Task.ts:4162), [тесты истории](../src/api/providers/__tests__/openai-codex-tool-history.spec.ts).

1. Одинаково обрабатывать terminal success, failed/error и incomplete в SDK и SSE, включая ошибку внутри response, а не только на верхнем уровне события.
2. EOF без подтверждённого завершения не превращать в успешный пустой/частичный ответ. Для раннего закрытия самим потребителем фиксировать отдельную причину, а не ложный успех.
3. Финализировать decoder и остаточный SSE-buffer; обрыв JSON не должен незаметно терять terminal event.
4. Освобождать/отменять reader и сетевой stream. SDK-stream и ручной SSE имеют эквивалентный контракт.
5. Проверить, как Task сохраняет уже исполненные tool calls/results при ошибке. Не восстанавливать «успешный результат» обычного инструмента и не повторять его автоматически.
6. Сохранить предыдущее ограниченное восстановление исторического завершения задачи; оно не заменяет новый lifecycle-контракт.

Тесты: terminal success/error/incomplete; вложенная ошибка; обрезанный поток; последний SSE-frame без перевода строки; поздние фрагменты после отмены; сохранение фактических результатов инструмента.

### Этап 9. Диагностика, интеграция и выпуск

1. Сохранить корреляцию из [диагностической реализации](../src/api/providers/openai-codex.ts:144), но довести семантику: ожидание, последний сетевой прогресс и длительность — разные величины.
2. Добавить безопасные категории OAuth/lock/retry/cancel/timeout; логировать поколение операции, но не токены, их хэши, account ID, prompt или сырые error bodies.
3. Подробные heartbeat ограничить диагностическим уровнем; обязательные отказы и повтор после частичного вывода должны оставаться заметными. Логирование не должно ломать запрос.
4. Прогнать целевые тесты Codex, OAuth, Task, wrappers, condense, cancellation и старой починки истории из правильных workspace; затем типы, линтер, форматирование и diff-check.
5. Провести локальную интеграционную проверку двух процессов и реального локального HTTP-сервера: максимум один refresh, независимая отмена, закрытие сокетов, ограниченный timeout.
6. Ручная проверка двух окон: параллельные разные задачи, отмена A при работе B, login/logout в одном окне, продолжение после восстановления связи. Не выводить production-токены и не принудительно ротировать их диагностическими скриптами.
7. Обновить все работающие окна одной исправленной версией: старое окно не соблюдает новый lock-протокол. Смешанные версии не считать поддержанной гарантией.
8. Добавить краткий patch changeset и отчёт: какие тесты реальные, какие mocked, какие сценарии с аккаунтом ещё не проверены.

## 5. Дополнительный этап только для Agent Manager

Файлы: [передача секретов](../src/core/kilocode/agent-manager/AgentManagerProvider.ts:849), [создание процесса](../src/core/kilocode/agent-manager/RuntimeProcessHandler.ts:297), [runtime](../packages/agent-runtime/src/process.ts), [host](../packages/agent-runtime/src/host/ExtensionHost.ts:1151).

Если требование включает дочерние агенты, не давать им независимо ротировать скопированный refresh-токен. Использовать существующий доверенный IPC: родитель получает согласованный снимок access token + account ID через основной OAuth-менеджер; ребёнок запрашивает его с корреляцией и ограниченным ожиданием. Для такого пути не передавать refresh-токен ребёнку. Отказ родителя — управляемая ошибка, а не попытка автономного refresh старой копии.

Нужны отдельные тесты двух детей, остановки родителя, отмены одного ребёнка, повторной авторизации и отсутствия токенов в IPC-логах. Не включать этот контракт в обычную файловую блокировку без явного этапа интеграции.

## 6. Разбиение на проверяемые изменения

1. OAuth: кэш, согласованный снимок и локальный single-flight.
2. OAuth: межоконная блокировка, согласованные писатели и безопасные ошибки.
3. Отмена: локальные options, Task → wrappers → Codex, корректная очистка.
4. Codex: request-local state, дедлайн SDK/SSE и завершение потока.
5. Retry: единая ограниченная политика без replay после частичного ответа на всех уровнях.
6. Интеграционные проверки, ограниченная диагностика и выпуск.

Каждое изменение начинается с падающего теста, сохраняет предыдущие проверки и не включает несвязанный рефакторинг. Не выпускать отдельную часть как полное исправление, пока верхние retry-слои продолжают обходить новый контракт.

## 7. Критерии окончательной приёмки

- Два локальных окна с одинаковым credential-доменом выполняют один refresh, а оба получают новую версию.
- Устаревшая операция не может удалить или воскресить credentials после нового login/logout.
- Отмена A закрывает её соединение и не влияет на B; поздние события A не меняют историю B или новую попытку A.
- Ни один partial response не склеивается с новым автоматически отправленным ответом; инструменты не переисполняются автоматически.
- SDK и SSE ограничены дедлайном, все повторные попытки ограничены общей политикой и завершают предшествующие ресурсы.
- 403 остаётся корректно диагностируемым отказом доступа, а не бесконечным retry или удалением авторизации.
- Диагностические тесты дефектов заменены регрессиями правильного поведения; нет тестов, требующих сохранить обнаруженный баг.
- Исходная починка истории продолжает проходить тесты; секреты и пользовательская история не мигрируются незаметно.

## 8. Источники решения

- [VS Code API: SecretStorage](https://code.visualstudio.com/api/references/vscode-api#SecretStorage): события изменения не являются транзакционной блокировкой.
- [Proper Lockfile](https://github.com/moxystudio/node-proper-lockfile): межпроцессный lock, heartbeat, stale recovery и обработка утраты lock.
- [OpenAI: обработка ограничений и ошибок](https://developers.openai.com/api/docs/guides/rate-limits): различать ошибки до начала stream и после получения вывода; не переигрывать автоматически потреблённый ответ.

План не является подтверждением исправления production-сбоев. Реализация и установка выполняются отдельным шагом после согласования.
