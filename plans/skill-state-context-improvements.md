# Анализ: улучшения контекстного флоу Kilo Code на основе статьи «SKILL.state: Scalable Long-Horizon Agent Skills»

## 1. Ключевые механизмы статьи

Статья (Badhe et al., arXiv:2608.26263v2) предлагает runtime, в котором на каждом шаге модель получает только три входа:

```
A_t = (P, Σ_t, O_t)
```

- `P` — неизменяемая процедурная спецификация (аналог системного промпта);
- `Σ_t` — явное структурированное состояние исполнения (мутабельный JSON по схеме домена);
- `O_t` — только последнее наблюдение.

Модель выдаёт `(R_t, ΔΣ_t, a_t)`: рассуждение, структурированный патч состояния и действие. После валидации патча рассуждение `R_t` **безвозвратно отбрасывается**, состояние обновляется словарным слиянием с семантикой `null`-удаления.

Ключевые результаты:

- промпт ограничен `O(1)`, кумулятивные токены `O(T)` против `O(T²)` у history-based рантаймов;
- на T=100: 65k токенов против 1.06M у Stateful-базлайна (16.2×);
- устойчивость к шуму: дистракторы отсеиваются на этапе генерации патча и не попадают в следующие промпты;
- восстановление после внешнего дрейфа состояния за 0 шагов (история не «перевешивает» свежие факты);
- **важный негативный результат**: при одинаковом токеновом бюджете (~1800 токенов) скользящее окно падает до 0.18, LLMLingua — до 0.22, summary-capped — до 0.52, тогда как структурированное состояние даёт 0.94. Вывод статьи: выигрывает не «короткий промпт», а **структурированное состояние как достаточная статистика**.

Ограничения статьи (раздел 7), критичные для переноса:

1. схема состояния должна быть известна заранее;
2. если значимость наблюдения не распознана в момент получения — оно не попадёт в состояние и будет потеряно;
3. задачи, где история сама является целью (аудит, объяснение прошлых действий), несовместимы с отбрасыванием истории.

## 2. Соответствие механизмов статьи и текущего флоу Kilo Code

| Механизм статьи                     | Аналог в Kilo Code                                                                                                                    | Статус                             |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `P` — неизменяемая спецификация     | системный промпт ([`SYSTEM_PROMPT()`](src/core/prompts/system.ts:183))                                                                | есть                               |
| `O_t` — последнее наблюдение        | текущий user-message + свежие `<environment_details>` ([`getEnvironmentDetails()`](src/core/environment/getEnvironmentDetails.ts:57)) | есть                               |
| `Σ_t` — структурированное состояние | частично: todoList в `environment_details` ([`formatReminderSection()`](src/core/environment/reminder.ts:6))                          | **слабое место**                   |
| Отбрасывание рассуждений после шага | нет: рассуждения и все наблюдения копятся в `apiConversationHistory`                                                                  | отсутствует                        |
| Валидация патча состояния рантаймом | нет эквивалента для состояния задачи                                                                                                  | отсутствует                        |
| Сжатие истории                      | [`summarizeConversation()`](src/core/condense/index.ts:237) — текстовый summary, т.е. аналог Memory-базлайна статьи                   | есть, но это «проигравший» базлайн |
| Скользящее окно                     | [`truncateConversation()`](src/core/context-management/index.ts:66) — по статье деградирует сильнее всего                             | есть как fallback                  |

Главный разрыв: текущий Kilo Code — классический «Stateful/ReAct» рантайм: состояние задачи распределено по текстовой истории и реконструируется моделью на каждом шаге. Статья показывает, что именно это — источник квадратичного роста токенов и «отравления контекста».

## 3. Что нельзя переносить напрямую

1. **Полный отказ от истории.** Задачи Kilo Code — открытое редактирование кода с пользователем в контуре: история диалога нужна для объяснений, откатов (checkpoints/rewind), аудита и пользовательского доверия. Это прямо попадает в ограничение №3 статьи. Полная замена истории состоянием неприменима.
2. **Жёсткая доменная схема.** В статье схема пишется один раз на домен (5 полей на все 100 CTF-задач). У Kilo Code задачи произвольные; фиксированная схема невозможна без динамического порождения схемы (ограничение №1 статьи).
3. **Отбрасывание рассуждений при нативном протоколе.** У Anthropic-моделей с extended thinking блоки thinking требуются для валидности последующих запросов (это уже обрабатывается в [`summarizeConversation()`](src/core/condense/index.ts:408)). Безусловно выбрасывать их нельзя.

## 4. Применимые улучшения (по убыванию ценности/риска)

### У1. Явный блок «состояние задачи» в каждом запросе (Σ_t) — главная идея

**Что:** расширить todoList до полноценного структурированного `task_state`, который рендерится в `environment_details` на каждом ходе:

- цель задачи (оригинальная формулировка);
- текущий план/прогресс (уже есть как todo);
- затронутые файлы и их статусы (прочитан/изменён/создан);
- принятые решения и ограничения;
- активные гипотезы/проверенные варианты (аналог `tested_hypotheses` из статьи — предотвращает повторение неудачных попыток, что дало +7.8 п.п. на CTF).

**Почему это работает по статье:** модель перестаёт реконструировать состояние из истории; свежие факты в состоянии перевешивают устаревшие наблюдения в истории (эффект восстановления за 0 шагов).
**Опора в коде:** инфраструктура уже есть — [`formatReminderSection()`](src/core/environment/reminder.ts:6) и [`UpdateTodoListTool`](src/core/tools/UpdateTodoListTool.ts:16) показывают рабочий паттерн «структурное состояние → каждый промпт → обновление инструментом».
**Риск:** низкий. История остаётся; блок состояния — дополнение.
**Метрика:** доля токенов промпта, приходящаяся на состояние; число повторов ранее неудачных действий.

### У2. Проекция результатов инструментов в состояние вместо хранения сырых наблюдений

**Что:** после каждого результата инструмента извлекать из него «существенное» (изменённые файлы, ошибки, факты) в `task_state`, а сырой объёмный вывод (длинные логи, полные листинги) помечать как кандидата на раннее вытеснение при condense.
**Почему:** в статье шум отсеивается на этапе генерации патча. В Kilo Code аналог — не позволять одноразовым наблюдениям (вывод `list_files`, `search_files` на 300 совпадений, длинные stdout) переживать свою полезность.
**Риск:** средний — нужна осторожность, чтобы не потерять детали, значимость которых проявится позже (ограничение №2 статьи). Митигация: вытеснять только при condense и сохранять вытесненное в недеструктивной истории (механизм `condenseParent` уже существует).

### У3. Структурированный формат summary вместо свободного текста

**Что:** перевести [`SUMMARY_PROMPT`](src/core/condense/index.ts:164) на выход в структурированном виде: сначала JSON-блок «состояние задачи» (факты, файлы, решения, незавершённое), затем краткая нарративная часть. При последующих ходах рендерить JSON-часть как блок состояния.
**Почему:** бюджет-эксперимент статьи (таблица 5) показывает, что «текстовый summary с жёстким потолком» (0.52) радикально хуже структурированного состояния (0.94) при том же бюджете. Текущий condense Kilo Code — именно текстовый summary.
**Риск:** низкий-средний; обратная совместимость сохраняется (summary остаётся текстовым блоком).

### У4. Защита от «шумовых» разделов в истории

**Что:** при сборке `environment_details` и tool results применять явные маркеры одноразового контента (например, оборачивать фоновую телеметрию терминалов, неиспользованные диагностические блоки) и гарантировать, что они не дублируются между ходами.
**Почему:** эксперимент 2 статьи: история с шумом деградирует с 0.68 до 0.53; состояние держит ≥0.97. В Kilo Code аналог шума — повторяющиеся/устаревшие секции окружения и многословные выводы команд.
**Риск:** низкий.

### У5. Валидация обновлений состояния рантаймом

**Что:** обновления `task_state` (через `update_todo_list` или новый инструмент) валидировать схемой (например, zod) в рантайме, а не доверять модели; невалидный патч → откат-повтор, как в статье.
**Почему:** таксономия ошибок статьи для малых моделей: 68% — преждевременная перезапись/удаление ключей состояния, 12% — синтаксис JSON. Валидация в рантайме защищает состояние от порчи моделью.
**Риск:** низкий; частично уже реализовано для todo ([`validateTodos`](src/core/tools/UpdateTodoListTool.ts:42)).

### У6. Починка мёртвого кода переполнения (не из статьи, но по теме)

В текущей ревизии [`handleContextWindowExceededError()`](src/core/task/Task.ts:4553) и константа `MAX_CONTEXT_WINDOW_RETRIES` не имеют найденных точек вызова, а результат [`checkContextWindowExceededError()`](src/core/task/Task.ts:5129) не используется. Любое улучшение контекстного менеджмента стоит предварить восстановлением этого пути.

## 5. Что НЕ стоит брать из статьи

- **Полное отбрасывание рассуждений** — ломает пользовательский UX (видимый reasoning), checkpoints/rewind и требования провайдеров к thinking-блокам.
- **Одну фиксированную схему на все задачи** — неприменимо к открытым задачам редактирования кода.
- **Оценки статьи как прямое обещание эффекта** — бенчмарки статьи (склад, CTF, τ-Bench) не совпадают с профилем «человек-в-контуре + редактирование файлов»; ожидаемый выигрыш в токенах для Kilo Code будет существенно меньше заявленных 16×, так как системный промпт и инструменты занимают большую постоянную часть промпта.

## 6. Предлагаемый порядок работ (для последующей реализации)

1. Восстановить вызов `handleContextWindowExceededError` в retry-пути (У6).
2. Расширить `task_state` (У1): тип в `@roo-code/types`, рендер в `environment_details`, инструмент обновления.
3. Перевести condense на структурированный выход (У3) и использовать его JSON-часть как источник `task_state` после сжатия.
4. Добавить проекцию результатов инструментов в состояние и маркеры одноразового контента (У2, У4).
5. Схема-валидация обновлений состояния (У5).
6. Тесты: unit на валидацию/рендер состояния; интеграционные на рост промпта (токены на шаг до/после); регрессия качества на типовых задачах редактирования.

## 7. Ожидаемый эффект

- Замедление роста промпта с числом ходов (состояние `O(1)` вместо реконструкции из истории) — основной выигрыш на длинных задачах.
- Меньше повторов неудачных действий за счёт явных «проверенных гипотез».
- Более качественный condense: структурированная часть переживает сжатие без потерь ключевых фактов.
- Устойчивость к устаревшим фактам в истории (свежее состояние перевешивает).

## 8. Количественная оценка выигрыша по контексту (У1–У4)

### 8.1. Базовая модель потребления (оценка, не факт)

Для длинной сессии примем типичные значения (подтверждено структурой кода, величины — оценка):

- системный промпт `S` ≈ 12–20k токенов — **фиксированная** часть каждого запроса (роль, инструменты, правила, MCP, skills);
- прирост за ход: ответ модели ≈ 0.5–1.5k + результаты инструментов ≈ 0.5–10k (одно `read_file` на 500 строк ≈ 3–6k; `search_files` — до нескольких тысяч);
- текущее управление: контекст растёт до порога condense (например, ~85–100% окна), затем [`summarizeConversation()`](src/core/condense/index.ts:237) сбрасывает его до «первое сообщение + summary + последние 3 сообщения» (~20–30k).

Кумулятивные входные токены ≈ Σ(размер контекста на каждом ходе). Поэтому выигрыш дают три рычага: (а) уменьшить стационарный размер контекста, (б) сократить число событий condense (каждое — отдельный LLM-вызов, читающий **всю** историю), (в) сократить число ходов за счёт меньшего числа повторных действий.

### 8.3. Сводный сценарий (оценка)

Сессия 30 ходов, окно 128k, порог ~85%:

- **Без изменений**: контекст циклически растёт до ~109k, 1–2 события condense; кумулятивно ≈ 30 × ~70k ≈ **2.0–2.2M входных токенов**.
- **У2**: чистый прирост за ход падает с ~4k до ~1.5k (сырые выводы вытесняются проекциями), condense 0–1 раз; кумулятивно ≈ **1.2–1.5M** → **−30–40%**.
- **У2+У1+У3**: добавляется снижение числа ходов на ~10% (меньше повторных действий) и более плотный пост-конденсационный контекст → **−40–50%** кумулятивно.
- **У4** вносит ≤3% сверх того.

### 8.4. Ограничения оценки

1. Цифры 8.2–8.3 — **расчётные оценки**, а не результаты измерений; реальный выигрыш зависит от доли tool outputs в конкретной задаче (для «разговорных» задач он близок к нулю, для задач с массовым чтением файлов — максимален).
2. Заявленные в статье 16× недостижимы для Kilo Code: там системная часть промпта мала, а у Kilo Code системный промпт + схемы инструментов — большая постоянная величина, которую У1–У4 не затрагивают.
3. Выигрыш У1 и У3 проявляется в основном как **сохранение качества** при меньшем контексте (меньше «потерянного в середине», меньше галлюцинаций на устаревших фактах), что не измеряется токенами напрямую.
4. Проверять эффект следует метриками: токены/ход, число condense на сессию, доля устаревших tool outputs в контексте, число повторных неуспешных действий, успех типовых задач редактирования.
