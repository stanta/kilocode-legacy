# План устранения регрессии отмены и завершения потока в 5.18.4

Дата: 2026-11-18. Статус: на согласовании. Production-код этим документом не изменяется.

## 1. Область и основание

Исправить три связанных дефекта из [отчёта сравнения](../docs/codex-5.18.4-regression-comparison-2026-11-18.md):

1. Технический abort транспорта подменяет исходную ошибку пользовательской отменой.
2. Abort при нормальном завершении конфликтует с предварительным чтением следующего фрагмента; теряется последний фрагмент или весь короткий ответ.
3. Запрет небезопасного replay переводит ошибку в старый внешний catch, который молча завершает цикл.

Минимальное воспроизведение на вложенных генераторах выполнено. Интеграционное воспроизведение реального Task — обязательный первый этап, а не уже выполненная проверка. Истинная первичная ошибка двух запросов пользователя не восстановлена.

Не включать в эту правку повторную реализацию OAuth, кэш моделей, оптимизацию общего состояния, статический парсер native tools или каталог моделей. Предыдущий [OAuth/lifecycle-план](codex-oauth-request-isolation-fix-plan.md) сохраняется как отдельный документ. Его реализованные защиты не откатывать.

## 3. Целевой контракт владения

### Логическая операция

Одна операция охватывает подготовку, первую сетевую попытку, разрешённые повторы и доставку результата. Её контроллер принадлежит внешнему циклу Task; его отменяет только явная остановка/уничтожение соответствующей задачи, а не cleanup отдельной попытки.

- В Task добавить минимальное приватное состояние активной операции: уникальная идентичность и контроллер.
- Создавать scope до запуска асинхронной подготовки, чтобы Stop во время подготовки также был наблюдаем.
- Передавать его сигнал во внутренние параметры [attemptApiRequest](../src/core/task/Task.ts:4900). Это локальное состояние, не часть API metadata или сохранённой истории.
- В рекурсивных разрешённых повторах сохранять этот scope и общий deadline.
- Прямые вызовы метода вне внешнего цикла, включая существующие тесты, получают собственный scope на весь вызов. Не создавать новый scope для каждого рекурсивного retry.
- Сохранить счётчик отмены подготовки: новый scope не должен обнулять уже произошедшую отмену.

### Транспортная попытка

У каждой HTTP-попытки отдельный контроллер. Текущее публичное поле контроллера можно сохранить для совместимости, но оно больше не служит источником пользовательского намерения для внешнего race.

- Логическая отмена распространяется вниз на transport; обратного распространения нет.
- Ошибка, EOF или закрытие iterator могут освободить transport, но не отменяют логическую операцию.
- Timeout остаётся типизированной ошибкой, а не пользовательским Stop.
- Старый finally очищает поле только при совпадении владельца. Он не отменяет новую попытку, соседнюю задачу или независимое сжатие.

Нельзя ограничиваться заменой текста ошибки, увеличением timeout, удалением сетевого abort или безусловным подавлением cancellation errors.

## 4. Шаги реализации

### Шаг 0. Зафиксировать базу и область изменения

1. Проверить текущие изменения, commit и версию сборки; не затрагивать чужие правки.
2. Сохранить связь с отчётом и двумя синтетическими воспроизведениями.
3. Не копировать реальную историю пользователя в fixtures. Использовать короткие искусственные сообщения и ошибки.
4. Не менять production credentials и не обращаться к серверу деплоя.

Результат: чисто выделенный patch с известной исходной версией.

### Шаг 1. Добавить падающие тесты через настоящий внешний цикл

Файлы: существующий [Task.spec.ts](../src/core/task/__tests__/Task.spec.ts:1020); новый планируемый [task-stream-lifecycle.spec.ts](../src/core/task/__tests__/task-stream-lifecycle.spec.ts).

1. Использовать реальный внешний метод чтения Task вместе с реальным внутренним генератором; подменять сеть и внешние сервисы, а не обе стороны найденной гонки.
2. Первый тест: provider отклоняет первый фрагмент типизированной ошибкой; внешний цикл сохраняет её причину, статус и признак retry.
3. Второй: provider отдаёт короткий корректный ответ и EOF; текст достигает представления/истории, пользовательская отмена не возникает.
4. Третий: полный вызов инструмента перед EOF обрабатывается один раз; нет ложной отмены и повторного исполнения.
5. Четвёртый: reasoning + text + usage + EOF доставляются без потери финальной статистики.
6. Пятый: явный 429 до ответа → закрытие первой попытки → второй успешный ответ, через внешний цикл.
7. Подтвердить ожидаемые падения до изменения реализации.

Почему новый уровень проверки обязателен: существующий [тест безопасного 429](../src/core/task/__tests__/Task.spec.ts:1044) вызывает внутренний генератор непосредственно и не включает внешний cancellation-race.

### Шаг 2. Разделить логическую отмену и transport cleanup

Файл: [Task.ts](../src/core/task/Task.ts:2821), внешний scope около [создания потока](../src/core/task/Task.ts:3429), параметры [attemptApiRequest](../src/core/task/Task.ts:4900).

1. Ввести контракт из раздела 3 без нового общего framework запросов.
2. При Stop отменять логическую операцию и текущий transport; существующую политику отмены сжатия сохранить.
3. Внешний waiter создаётся один раз из стабильного сигнала операции, а не лениво из изменяемого контроллера транспорта.
4. Внутренний сигнал попытки передаётся провайдеру через существующие local request options.
5. Отмена при подготовке и retry delay останавливает будущий dispatch.
6. Удалять слушатели и ссылки владельца при завершении операции; исключить повторную регистрацию на каждом chunk.

Приёмка: техническая очистка попытки не отвергает внешний waiter. Настоящий Stop немедленно заканчивает ожидание даже у provider, который ещё не вернул первый фрагмент.

### Шаг 3. Исправить порядок чтения и финальный chunk

Файл: [основной цикл](../src/core/task/Task.ts:3479).

1. Убрать чтение следующего фрагмента до обработки уже полученного.
2. Обрабатывать текущий chunk, затем проверять остановку/отклонение инструмента и только потом читать следующий.
3. Для пустого chunk обеспечить продвижение iterator; перестановка не должна создать бесконечный continue.
4. Полученный EOF трактовать как завершение, а не как cancellation. Реальный Stop проверять перед обработкой новых tool events, чтобы не выполнять их после отмены.
5. Проверить все выходы из большого switch и цикла: обычное завершение, отклонение инструмента, выполнение разрешённого инструмента, ошибка и отмена.

Приёмка: короткий ответ отображается до завершения потока; последний text/tool/usage не теряется.

### Шаг 4. Согласовать фоновый сбор usage и единственного читателя

Файл: [drainStreamInBackgroundToFindAllUsage](../src/core/task/Task.ts:3856).

1. При нормальном EOF не запускать новое чтение законченного iterator.
2. При реальной отмене не запускать сбор статистики, который удерживает соединение.
3. При существующем намеренном раннем выходе основного цикла разрешать только явную передачу владения iterator сборщику usage. Удалённый prefetch больше не предоставляет ему заранее полученный item.
4. Обеспечить конечное ожидание каждого pending read через abortable race, а не только проверку времени между фрагментами.
5. Сборщик не исполняет инструменты и не добавляет текст в основной ответ. Статистика не учитывается дважды.
6. Когда сбор закончен или истёк его бюджет, закрыть только transport данной операции. Не очищать контроллер более нового запроса.
7. Проверить пересечение фонового drain с новым запросом на handler: нельзя создавать скрытый второй активный запрос. Если bounded drain и новая попытка конфликтуют, сначала завершить/отменить старый drain согласно контракту.

Приёмка: у iterator в каждый момент один читатель; нет открытого сокета/таймера после Stop; данные usage относятся к правильной API-строке.

### Шаг 5. Исправить очистку и сохранение причины

Файл: [catch первого фрагмента](../src/core/task/Task.ts:5342), [finally потока](../src/core/task/Task.ts:5546), [Codex createMessage](../src/api/providers/openai-codex.ts:177).

1. Захватить исходную ошибку и её классификацию до cleanup. Cleanup не заменяет её своим abort/error.
2. При ошибке отменять только transport конкретной попытки, затем закрывать iterator.
3. Перед разрешённым повтором сохранить подтверждение закрытия старой попытки и конечный бюджет ожидания. Не запускать retry после неопределённого закрытия.
4. При normal EOF освободить ресурсы без отмены логической операции. Вызов transport abort допустим лишь как локальная очистка и не должен быть наблюдаем как пользовательская отмена.
5. При раннем выходе потребителя сначала закрыть transport, затем iterator; не полагаться на finally делегирования, если pending read препятствует его выполнению.
6. Ошибка cleanup логируется безопасно как вторичная; основная ошибка сохраняет статус, тип и retry-политику.
7. Не использовать пустые catch для новой логики и не добавлять тестовые методы в production-классы.

Приёмка: первая ошибка, ошибка середины потока и EOF различимы; все ресурсы закрыты; позднее завершение не затрагивает новую операцию.

### Шаг 6. Сохранить безопасную retry-политику

Файлы: [первый retry](../src/core/task/Task.ts:5347), [backoff](../src/core/task/Task.ts:5567), [virtual-quota wrapper](../src/api/providers/virtual-quota-fallback.ts:75).

1. HTTP 429/допустимый 5xx до ответа остаются ограниченно повторяемыми с тем же логическим scope и deadline.
2. Ошибка OAuth, HTTP 403, timeout и неопределённый исход не превращаются в cancellation; интерфейс видит их собственную категорию.
3. После reasoning/text/tool output автоматический replay запрещён независимо от auto-approval и wrapper.
4. Очистка попытки N не отменяет попытку N+1. Stop во время backoff запрещает N+1.
5. Wrapper передаёт request options и типизированную ошибку, не выполняет скрытое переключение провайдера.
6. Проверить обычные non-Codex провайдеры: изменение общего Task не должно ломать их существующую retry-политику и context-window recovery.

Тесты: дополнить [Task.spec.ts](../src/core/task/__tests__/Task.spec.ts:1044), сохранить [virtual-quota-codex-retry.spec.ts](../src/api/providers/__tests__/virtual-quota-codex-retry.spec.ts) и [context-window-overflow-recovery.spec.ts](../src/core/task/__tests__/context-window-overflow-recovery.spec.ts).

### Шаг 7. Явно завершать Task и показывать продолжение

Файлы: [обработка streaming error](../src/core/task/Task.ts:4045), [внешний catch](../src/core/task/Task.ts:4503), [существующий abort/rehydrate-путь](../src/core/webview/ClineProvider.ts:285), [UI ошибок](../webview-ui/src/components/chat/ChatView.tsx:347).

1. Определять пользовательскую отмену по явному намерению/сигналу операции, не по локальному состоянию transport после cleanup и не по строке ошибки.
2. Сохранить оригинальную безопасную причину в строке API-запроса. Timeout — не user-cancelled.
3. Для terminal Codex error убрать путь «просто throw → внешний return true». Использовать единый существующий механизм завершения/восстановления задачи и её состояния ожидания продолжения.
4. До остановки сохранить уже принятые assistant chunks и фактические результаты инструментов, если они есть. Не генерировать успешные результаты отсутствующих инструментов.
5. Не объявлять TaskCompleted для ошибки. Состояния streaming, ожидания первого chunk и блокировки UI должны завершиться согласованно.
6. Для отказа до ответа — понятное сообщение и ручная повторная попытка, когда она допустима. Для частичного/неопределённого исхода — явное продолжение с предупреждением, а не автоматическое переисполнение.
7. Не позволять auto-approval автоматически принимать unsafe continuation. После повторного открытия нельзя терять предупреждение о частично выполненных действиях.
8. Событие конечного состояния отправлять один раз. Не восстанавливать старую задачу поверх уже выбранной новой; сохранить проверку instance ownership в provider.
9. Если существующих UI-сообщений достаточно, не добавлять новый публичный протокол. Новое поле вводить только при необходимости выразить безопасность ручного продолжения.

Приёмка: ошибка видна пользователю, нет вечной занятости или «тишины», кнопка продолжения не запускает опасный replay, состояние корректно после reload.

### Шаг 8. Сделать диагностику наблюдаемой в установленной сборке

Файлы: [диагностика Codex](../src/api/providers/openai-codex.ts:214), [инициализация Output](../src/extension.ts), [Task](../src/core/task/Task.ts).

1. Провести события жизненного цикла в существующий постоянный Kilo-Code Output/logger. Не рассчитывать, что console.info обязательно попадёт в доступные журналы.
2. Использовать один request/operation ID от подготовки Task до конца транспорта; отдельный номер попытки.
3. События: подготовка начата/завершена, авторизация, dispatch, первый chunk, EOF, исходная ошибка, пользовательский Stop, начало/конец cleanup, конечное UI-состояние.
4. Записывать build/version, процесс, task/instance ID, категорию ошибки и безопасный HTTP-статус. Не писать токены, prompt, аргументы, сырые error bodies.
5. Ограничить частоту heartbeat и гарантировать, что сбой логирования не меняет исход запроса.

Приёмка: на установленном VSIX по одному ID восстанавливается путь короткого успеха, первой ошибки и отмены; ошибку больше невозможно спутать с техническим abort.

### Шаг 9. Проверить, выпустить и подтвердить на двух окнах

1. Сначала targeted Task lifecycle, затем имеющиеся Codex transport/isolation/history tests, wrapper, condense и context-window recovery.
2. Добавить UI-интеграцию: реальное сообщение об окончании ошибки выводит чат из занятого состояния и сохраняет доступность безопасного действия.
3. Локальный HTTP-сервер: нормальный EOF, ошибка до ответа, зависшее чтение, Stop, короткий tool-call, закрытие TCP. Искусственный provider без поддержки abort проверяет ограниченность внешнего ожидания и отсутствие нового dispatch.
4. Проверки типов, ESLint без отключения правил, форматирование и diff-check. Запуск backend-тестов из workspace [src](../src/package.json), UI-тестов из [webview-ui](../webview-ui/package.json).
5. Добавить patch changeset; Kilo-specific изменения пометить согласно правилам проекта.
6. Проверить номер версии и fingerprint установленного bundle в каждом окне. Установка/перезапуск рабочих окон — отдельное согласованное действие, не часть автоматического unit-теста.
7. Ручной smoke-test: короткая новая задача без доступа к серверу, нормальный ответ, повторяемая синтетическая ошибка, Stop только в A при продолжающемся B, затем открытие завершённой задачи и сжатие.
8. Повтор исходного запроса про деплой только после согласования пользователем и обычного контроля разрешений инструментов. Само сравнение логов не разрешает доступ к инфраструктуре.

## 5. Матрица обязательных регрессий

| Сценарий                       | Что проверяется                                            |
| ------------------------------ | ---------------------------------------------------------- |
| Ошибка до первого chunk        | Исходный объект/тип и статус сохраняются, ложного Stop нет |
| Короткий text + EOF            | Текст доставлен, завершение успешно                        |
| Полный tool-call + EOF         | Вызов представлен/исполнен один раз; история согласована   |
| Reasoning + text + usage       | Последний chunk и usage не потеряны                        |
| Частичный ответ + ошибка       | Принятые данные не потеряны, автоматического replay нет    |
| 429 → успех                    | Старый transport закрыт до нового, внешний цикл не отменён |
| Stop до dispatch               | HTTP не отправлен                                          |
| Stop во время read/backoff     | Ожидание завершается; нового запроса нет                   |
| Ошибка/зависание cleanup       | Оригинальная ошибка сохраняется; unsafe retry запрещён     |
| Поздний finally старой попытки | Новый controller и задача не затронуты                     |
| Две задачи A/B                 | Отмена A не отменяет B                                     |
| Ошибка + auto-approval         | Не запускается автоматическое небезопасное продолжение     |
| Terminal error + reload        | Ошибка и безопасное действие остаются доступны             |
| Non-Codex + context overflow   | Существующая восстановительная логика не сломана           |

## 6. Порядок поставки

1. Падающие интеграционные тесты внешнего цикла.
2. Разделение cancellation scopes и сохранение причины.
3. Порядок обработки chunks, нормальный EOF и владение usage-drain.
4. Явное конечное состояние задачи/UI и проверка retry-политики.
5. Постоянная диагностика, регрессии других провайдеров и проверенная сборка.

Не выпускать только изменение текста ошибки или только снятие UI-блокировки: это скроет потерю ответа. Не откатывать защиту от повторного исполнения инструментов ради возвращения внешне работающего цикла.

## 7. Итоговая приёмка

Исправление принято, когда реальный внешний цикл Task сохраняет исходную ошибку, доставляет все допустимые фрагменты на нормальном EOF, закрывает transport при Stop, не переигрывает частичный ответ и оставляет интерфейс в определённом состоянии. Проверка должна включать установленную сборку в двух окнах; одних provider-unit-tests недостаточно.

Этот план исправляет воспроизведённый механизм регрессии. Он не утверждает, что первоначальной причиной конкретных пользовательских запросов был HTTP 403, OAuth-lock или таймаут: эти данные были потеряны в существующей обработке ошибок.
